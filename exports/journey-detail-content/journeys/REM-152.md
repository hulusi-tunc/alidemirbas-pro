## REM-152 — Return Request

- Canonical ID: `REM-152`
- Slug: `return-authorization`
- Display name: Return Request
- Canonical name (chain form): Return request → eligibility → authorize, reject or review
- Source route: `/lab/customer-journeys/return-authorization`
- Category: Returns, remedies, corrections & post-completion recovery
- Goal: eligibility-qualification
- Channels: task, email
- Surface: customer (communicating)

**Purpose**: Decide whether something may enter a return process, as a decision separate from whether money is owed.

> Decide whether something may enter a return process, as a decision separate from whether money is owed.

### Trigger
- Event: `return_requested`
- Meaning: a request to send back an identified item, resource or deliverable
- Not enough on its own: an expression of dissatisfaction, which is a report rather than a request to return anything
- Requires: a request to send back an identified item, resource or deliverable
- Source: declared

### Entity
- Scope: the return request and the original fulfillment it concerns
- instance: return_request_id · one-active-per-key

### Who enters

- no instance of this journey is already open for the the return request and the original fulfillment it concerns
- hard gates (GLB-31) allow communication for this purpose

### Suppressed when
- [canonical rule] A return requested is not a return authorized.
- [canonical rule] Return eligibility rules are never invented.
- [canonical rule] Refund eligibility and return eligibility may be different decisions with different answers.

   - sent on classification - no wait before it

**Channel roles** (recommended default)

### Reusable rule
A return request creates a decision about whether the original fulfillment may enter a return process; it does not itself reverse the fulfillment.

### Entity (notes)
- the return request and the original fulfillment it concerns
- Return eligibility and refund eligibility are different questions with different rules. Authorising a return decides only the first.

### Distinct from
- REM-153 (Return authorized → in transit, received, lost or expired) — This grants permission for a resource to come back. REM-153 tracks whether it actually does, which fails independently and often.

### Guardrails
1. A return requested is not a return authorized.
2. Return eligibility rules are never invented.
3. Refund eligibility and return eligibility may be different decisions with different answers.

### Technical logic (graph, 17 nodes)
- **t.requested** [trigger] (entry, evidence: declared)
  - Event id: `return_requested`

  - evidence: declared

  - not enough on its own: an expression of dissatisfaction, which is a report rather than a request to return anything
  - -> a.capture (node)
- **a.capture** [action]

  - writes return_log (append)
  - -> c.applicable (node)
- **c.applicable** [condition] (2 branches)
  - Does a return process apply to this at all?
  - -> c.policy [Returnable]: the thing exists physically or as a revocable deliverable and can be sent back (node)
  - -> h.alternative [Nothing to return]: the delivery was a service performed, a consumed resource, or something with no return path (node)
- **c.policy** [condition] (2 branches)
  - Is a return eligibility policy defined for this?
  - -> c.eligible [Defined]: policy states what may be returned, within what window and on what conditions (node)
  - -> h.undefined [Not defined]: no policy covers returns of this kind (node)
- **h.alternative** [handoff]
  - Remedy selection → resolve obligation → financial handoff if needed
  - Detail: a return requested against something that cannot be returned
  - carries: the request and the unresolved obligation behind it - original_fulfillment_id becomes REM-157's obligation_id
  - carries: the fact that no return route exists, so the remedy is something else rather than nothing
  - carries: a fresh issue_id, minted at this handoff and deterministically derived from return_request_id - REM-152 has no issue concept of its own, so REM-157's instance is opened here rather than carried
  - -> REM-157 (journey)
- **c.eligible** [condition] (3 branches)
  - What does the policy determine?
  - -> a.authorize [Eligible]: the policy's conditions are met deterministically (node)
  - -> a.reject [Ineligible]: the policy rules it out deterministically (node)
  - -> a.review [Requires review or evidence]: the policy leaves this case to a decision rather than a rule (node)
- **h.undefined** [handoff]
  - Decision request → validate → route, reject or hold
  - Detail: a return request with no governing eligibility policy
  - carries: the request and the original fulfillment
  - carries: the explicit fact that no eligibility rule was invented in order to decide it
  - -> DEC-181 (journey)
- **a.authorize** [action]
  - Record RETURN_AUTHORIZED with the scope, the method and the validity. Authorising a return permits the resource to come back and decides nothing about whether money is owed - refund eligibility is a separate question with its own rules and its own answer
  - writes return_log (append)
  - -> a.notify-authorization (node)
- **a.reject** [action]
  - Record RETURN_REJECTED with the reason drawn from the policy that ruled it out
  - writes return_log (append)
  - -> a.notify-rejection (node)
- **a.review** [action] (execution: human)
  - Record RETURN_UNDER_REVIEW and gather what the decision requires. Nothing is authorised while it is under review
  - writes return_log (append)
  - -> w.decision (node)
- **a.notify-authorization** [action] (execution: communication)
  - Tell the requester the return is authorised, within what scope and by what method, and that authorisation permits the resource to come back without deciding that money is owed. Leaving them to discover the answer from the transit lifecycle makes the next step arrive before the decision does

- **a.notify-rejection** [action] (execution: communication)

- **w.decision** [wait]

  - Detail: timeout after The decision SLA. (configure return_authorization.decision)

  - engagement does not extend the window
  - -> c.decision [on event] (node)
  - -> h.escalate [on timeout] (node)
- **h.transit** [handoff]

- **x.rejected** [exit]

- **c.decision** [condition] (2 branches)

  - -> a.reject [Rejected]: the reviewer refused it (node, back-edge)
