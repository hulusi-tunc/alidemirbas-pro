## ACC-263 — Activation Reminder

- Canonical ID: `ACC-263`
- Slug: `entitlement-activation-window`
- Display name: Activation Reminder
- Canonical name (chain form): Entitlement or credential issued → activation window → activated or lapsed unclaimed
- Source route: `/lab/customer-journeys/entitlement-activation-window`
- Category: Access, entitlement, credentials & capability
- Goal: progression-milestone
- Channels: email, in-app
- Surface: customer (communicating)

**Purpose**: Get somebody to actually use what they have been granted, before the window in which they can claim it closes - because an unredeemed entitlement is indistinguishable from one that was never granted.

> Get somebody to actually use what they have been granted, before the window in which they can claim it closes - because an unredeemed entitlement is indistinguishable from one that was never granted.

### Trigger
- Event: `entitlement_provisioned_and_reachable`
- Meaning: an entitlement or credential authoritatively granted to a named holder; confirmation that it is provisioned and reachable by that holder; an activation window or expiry
- Not enough on its own: an eligibility decision with no provisioning behind it; a grant whose resource is not yet reachable
- Requires: an entitlement or credential authoritatively granted to a named holder; confirmation that it is provisioned and reachable by that holder; an activation window or expiry
- Source: authoritative

### Entity
- Scope: the issued entitlement or credential and its activation window
- instance: entitlement_id + holder_id · one-active-per-key

### Who enters
- an entitlement or credential authoritatively granted to a named holder
- confirmation that it is provisioned and reachable by that holder
- an activation window or expiry
- no instance of this journey is already open for the the issued entitlement or credential and its activation window
- hard gates (GLB-31) allow communication for this purpose

### Suppressed when
- [canonical rule] One reminder, never two. The window is the pressure; repetition is not.
- [canonical rule] A holder who has used this capability before is not re-onboarded onto it.
- [canonical rule] Lapsed-unclaimed and revoked-before-use are recorded as different outcomes - one is about the holder, the other is not.
- [canonical rule] The message names one action, not the full capability surface.

### Recommended orchestration · offer-decide-remind
1. **ready** (service, canonical rule)

   - checks: Is this the holder's first entitlement of this kind?

   - destination: `first-use-action` · bound to `entitlement_id`
2. **brief** (service, canonical rule)
   - sent on classification - no wait before it
   - checks: Is this the holder's first entitlement of this kind?
   - Channel roles: persistent -> in-session
   - Purpose: Confirm the new grant briefly and name only what changed from what they already had.
3. **remind** (service, canonical rule)
   - Timing: The single reminder is placed before the activation window closes, late enough that the first notice has had its chance and early enough that claiming is still possible. (configure entitlement_activation.first_use) (relative to activation_window_ends_at)
   - cancelled by the granted capability is used for the first time; the entitlement is revoked or replaced
   - re-read before sending: the the issued entitlement or credential and its activation window re-read from the system of record before acting on the timeout
   - checks: Is there still time to claim it?
   - Channel roles: persistent -> in-session
   - Purpose: Send one reminder naming the deadline and the same single first action.
   - destination: `first-use-action` · bound to `entitlement_id` · must not claim: a moved deadline

**Channel roles** (recommended default)
- persistent (email) — the message has to be kept and survive until the person can act on it
- in-session (in-app) — the person is active in the product and the action is taken there
- delivery fallback: same-role-other-channel

### Stops when
- [success] activated (re-entry: a further entitlement to the same holder is a new instance)
- [invalid-state] entitlement withdrawn before use (re-entry: a reissued entitlement starts a fresh window)
- [timeout] lapsed unclaimed (re-entry: a new grant of the same capability starts a new window)

### Configure
- `entitlement_activation.first_use` [config required] (reminder-before-attribute): configure entitlement_activation.first_use — The single reminder is placed before the activation window closes, late enough that the first notice has had its chance and early enough that claiming is still possible.
- `entitlement_activation.last_chance` [config required] (attribute-bound): configure entitlement_activation.last_chance — After the reminder the instance waits until the activation window itself closes; there is no second reminder.
- `entitlement_activation.touches` [recommended default]: 2 — Every touch runs against a budget fixed when the instance opened; the budget is the plan's own length, and no touch is repeated because nothing could tell whether it arrived.
- `entitlement_activation.cooldown` [recommended default]: none — This journey is per the issued entitlement or credential and its activation window; a later instance concerns a different the issued entitlement or credential and its activation window and no cooldown applies between them.

### Reusable rule
A granted capability nobody has used is not yet a benefit, and the activation window is the only period in which saying so still helps.

### Entity (notes)
- the issued entitlement or credential and its activation window
- One issuance, one window. A reissued credential is a new instance and does not inherit the old window.

### Distinct from
- ACC-72 (Entitlement grant → provision → verify availability) — ACC-72 provisions the capability and confirms it is technically reachable. This starts once that is true and is about whether the holder ever uses it.
- ACC-76 (Credential issued → activate → use, expire or revoke) — ACC-76 tracks the credential's own issue/expire/revoke lifecycle. Here the only question is first use inside the window.

### Guardrails
1. One reminder, never two. The window is the pressure; repetition is not.
2. A holder who has used this capability before is not re-onboarded onto it.
3. Lapsed-unclaimed and revoked-before-use are recorded as different outcomes - one is about the holder, the other is not.
4. The message names one action, not the full capability surface.
