## SCH-282 — Availability Search Abandonment

- Canonical ID: `SCH-282`
- Slug: `availability-searched-no-booking`
- Display name: Availability Search Abandonment
- Canonical name (chain form): Availability searched, no booking → nearest window or waitlist
- Source route: `/lab/customer-journeys/availability-searched-no-booking`
- Category: Scheduling, appointments, reservations & time-bound commitments
- Goal: scheduling-commitment
- Channels: email, push
- Surface: customer (communicating)

**Purpose**: Follow up an availability question that produced no booking with something that is genuinely bookable now, or with a waitlist place where nothing fits - because what was shown was never held and is probably already gone.

> Follow up an availability question that produced no booking with something that is genuinely bookable now, or with a waitlist place where nothing fits - because what was shown was never held and is probably already gone.

### Trigger
- Event: `availability_query_closed_without_reservation`
- Meaning: an availability query recorded for a named person against a specific resource and window; no reservation or hold created by that person for that window since
- Not enough on its own: a query by somebody who already holds a booking for that window; a browse with no resource or window attached to it
- Requires: an availability query recorded for a named person against a specific resource and window; no reservation or hold created by that person for that window since
- Source: behavioral

### Entity
- Scope: the availability question, the resource and window it asked about, and the absence of any reservation from it
- instance: person_id + availability_query_id · one-active-per-key

### Who enters
- an availability query recorded for a named person against a specific resource and window
- no reservation or hold created by that person for that window since
- no instance of this journey is already open for the the availability question
- hard gates (GLB-31) allow communication for this purpose

### Suppressed when
- [canonical rule] Availability is re-evaluated before the offer is sent. What the query returned was never held and is not evidence of anything now.
- [canonical rule] A different window is labelled as a different window.
- [canonical rule] A waitlist place is stated as reserving nothing.
- [canonical rule] One offer per query. A second offer for the same request is pressure rather than help.
- [canonical rule] The delay before the offer is bounded and never extended by the person browsing again.

**Channel roles** (recommended default)

### Stops when
- [no-action] no offer made; the query cannot be attributed to a reachable person (re-entry: a later query from an identified person qualifies normally)
- [success] booked; no offer was needed (re-entry: a later query with no booking behind it starts a new instance)
- [success] waitlisted; nothing is reserved (re-entry: capacity reaching the waitlist is that mechanism's business, not a new instance of this one)
- [no-action] nothing to offer; no message sent (re-entry: a later query for a window that does have capacity qualifies again)
- [timeout] offer made and not taken (re-entry: a new availability query is a new instance; this one is never re-offered)

### Reusable rule
An answer about availability holds nothing, so anything sent afterwards has to be re-checked before it is offered.

### Entity (notes)
- the availability question, the resource and window it asked about, and the absence of any reservation from it
- The question is not a claim on anything. A second question about a different window is its own instance and never inherits the first one's offer.

### Distinct from
- SCH-171 (Availability query → evaluate capacity → offer valid options) — SCH-171 answers the question at the moment it is asked and holds nothing. This journey starts only once that answer has produced no booking, and it re-evaluates from scratch rather than reusing what was shown.
- SCH-172 (Slot hold → reserve temporarily → confirm, expire or release) — SCH-172 holds capacity for somebody who asked for it. Nothing here is held at any point, and the offer says so.

### Guardrails
1. Availability is re-evaluated before the offer is sent. What the query returned was never held and is not evidence of anything now.
2. A different window is labelled as a different window.
3. A waitlist place is stated as reserving nothing.
4. One offer per query. A second offer for the same request is pressure rather than help.
5. The delay before the offer is bounded and never extended by the person browsing again.
