## TRM-275 — Data Deletion Confirmation

- Canonical ID: `TRM-275`
- Slug: `deletion-request-confirmation`
- Display name: Data Deletion Confirmation
- Canonical name (chain form): Deletion request → verify requester → confirm scope and retention → closed
- Source route: `/lab/customer-journeys/deletion-request-confirmation`
- Category: Entity merge, account closure, data lifecycle & terminal states
- Goal: consent-permission
- Channels: email
- Surface: customer (communicating)

**Purpose**: Give the person who asked for their data to be removed a durable record of what went, what stayed, under which obligation, and the date the request closed - because a deletion nobody can point to is indistinguishable from one that never happened.

> Give the person who asked for their data to be removed a durable record of what went, what stayed, under which obligation, and the date the request closed - because a deletion nobody can point to is indistinguishable from one that never happened.

### Trigger
- Event: `data_deletion_requested_by_subject`
- Meaning: a deletion request recorded against a named data subject; the scope the request itself names; the response window the governing obligation sets

- Requires: a deletion request recorded against a named data subject; the scope the request itself names; the response window the governing obligation sets
- Source: declared

### Entity
- Scope: the data subject and the single deletion request they raised, bounded by the scope that request names
- instance: deletion_request_id · one-active-per-key

### Who enters

- the scope the request itself names
- the response window the governing obligation sets
- no instance of this journey is already open for the the data subject and the single deletion request they raised
- hard gates (GLB-31) allow communication for this purpose

### Suppressed when
- [canonical rule] Nothing is deleted on an unverified request, and nothing is asked for beyond the proof of control the obligation actually requires.
- [canonical rule] Ending the relationship is not a deletion request and is never answered as one.
- [canonical rule] No retention is described that an authoritative obligation does not require. Where the policy is silent, nothing is claimed.
- [canonical rule] The response window belongs to the obligation, not to the work. It is answered inside it or escalated at it.
- [canonical rule] The closing message is a record: scope, outcome, obligation, date - readable a year later by somebody who was not there.

### Reusable rule
A deletion is only honoured if the person who asked can be told exactly what went, what stayed, and under whose rule it stayed.

### Entity (notes)
- the data subject and the single deletion request they raised, bounded by the scope that request names
- One request, one record. A later request from the same person is a separate instance and inherits neither this one's verification nor its window.

### Distinct from
- TRM-109 (Data deletion request → validate scope → hold, delete or retain required data) — TRM-109 decides what the request covers, what an authoritative obligation requires keeping, and executes the removal. This journey is only what the requester is told, and it states nothing TRM-109 has not resolved.

4. The response window belongs to the obligation, not to the work. It is answered inside it or escalated at it.

### Technical logic (graph, 13 nodes)
- **t.request** [trigger] (entry, evidence: declared)
  - Event id: `data_deletion_requested_by_subject`
  - Data deletion requested by subject
  - evidence: declared
  - requires: a deletion request recorded against a named data subject
  - requires: the scope the request itself names
  - requires: the response window the governing obligation sets
  - not enough on its own: a closure of the relationship
  - not enough on its own: a request to stop receiving messages
  - not enough on its own: a support conversation that mentions deletion
  - -> a.acknowledge (node)
- **a.acknowledge** [action] (execution: communication)
  - Acknowledge the request, state the date by which the obligation requires an answer, and say that establishing who is asking comes first. An unacknowledged request leaves the person unable to tell a mandated wait from being ignored
  - -> c.verified (node)
- **c.verified** [condition] (2 branches)
  - Is the requester's control of the named scope already established?
  - -> w.decision [Already established]: control of the account or authority over the named scope meets the standard the obligation requires (node)
  - -> a.verify [Not yet established]: the request arrived without sufficient proof that the requester controls what they are asking to erase (node)
- **w.decision** [wait]
  - until scope, retained items and deletion outcome are all resolved
  - Detail: timeout after The resolution is waited for until the response deadline the governing obligation sets; reaching it unanswered escalates to data-protection ownership. (configure deletion_request.decision)
  - the window belongs to the obligation rather than to how long the work takes, and passing it in silence is itself the failure
  - engagement does not extend the window
  - -> c.outcome [on event] (node)
  - -> h.overdue [on timeout] (node)
- **a.verify** [action] (execution: communication)
  - Ask for exactly the proof of control the obligation requires and nothing beyond it. Collecting extra identifying data in order to honour a deletion request is the contradiction the request exists to end
  - -> w.verify (node)
- **c.outcome** [condition] (2 branches)
  - What does the resolved outcome actually say?
  - -> a.closed-full [Deleted in full]: everything in the named scope was deleted and no retention obligation covers any of it (node)
  - -> a.closed-partial [Partly retained]: an authoritative retention obligation covers part of the named scope (node)
- **h.overdue** [handoff] (external)
  - external:data-protection-escalation
  - Detail: a deletion request that reaches its mandated response window with no authoritative outcome to state
  - carries: the request, its scope, its window and what the requester has already been told
  - carries: which part of the scope remains unresolved and who holds it
  - -> external:data-protection-escalation (external)
- **w.verify** [wait]
  - until sufficient proof of control or identity is provided
  - Detail: timeout after The verification period held inside the mandated response window. (configure deletion_request.verify)
  - the response window runs whether or not the requester replies, so an unverifiable request has to be closed inside it rather than left open
  - engagement does not extend the window
  - -> w.decision [on event] (node, back-edge)
  - -> a.unverified [on timeout] (node)
- **a.closed-full** [action] (execution: communication)
  - Confirm what was deleted, the scope it covered and the date the request closed. This message is the record the requester keeps, so it states the outcome rather than thanking them for their patience
  - -> x.closed (node)
- **a.closed-partial** [action] (execution: communication)
  - State what was deleted, what is retained, which obligation requires it and when that obligation ends. Naming the obligation is what makes retention a rule rather than a preference
  - -> x.closed (node)
- **a.unverified** [action] (execution: communication)
  - Close the request as unverified, saying plainly that nothing was deleted, why, and that a fresh request can be raised at any time. A silent close reads as a deletion that happened
  - -> x.unverified (node)
- **x.closed** [exit] (terminal)
  - answered and closed on the record
  - Detail: a later deletion request from the same person is a new instance, verified again from the start
- **x.unverified** [exit]
  - closed unverified, nothing deleted
  - Detail: a fresh request from the same person is a new instance with its own window and its own verification
