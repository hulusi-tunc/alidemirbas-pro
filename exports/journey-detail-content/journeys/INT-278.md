## INT-278 — Integration Setup

- Canonical ID: `INT-278`
- Slug: `integration-setup-outcome`
- Display name: Integration Setup
- Canonical name (chain form): Integration connection started → validation outcome → active or targeted fix
- Source route: `/lab/customer-journeys/integration-setup-outcome`
- Category: Integrations, synchronization, external systems & data consistency
- Goal: progression-milestone
- Channels: email, in-app
- Surface: customer (communicating)

**Purpose**: Tell the person who started a connection which stage it actually failed at and what would fix that stage - because a generic failure sends a capable person to support and an incapable one away for good.

> Tell the person who started a connection which stage it actually failed at and what would fix that stage - because a generic failure sends a capable person to support and an incapable one away for good.

### Trigger
- Event: `integration_connection_attempt_resolved`
- Meaning: a connection attempt recorded against a named integration by a named configurer; a recorded outcome from the authentication, scope and capability checks
- Not enough on its own: an integration browsed or selected; a credential entered but never submitted
- Requires: a connection attempt recorded against a named integration by a named configurer; a recorded outcome from the authentication, scope and capability checks
- Source: authoritative

### Entity
- Scope: the single connection attempt and the integration it configures
- instance: connection_attempt_id · one-active-per-key

### Who enters
- a connection attempt recorded against a named integration by a named configurer
- a recorded outcome from the authentication, scope and capability checks
- no instance of this journey is already open for the the single connection attempt and the integration it configures
- hard gates (GLB-31) allow communication for this purpose

### Suppressed when
- [canonical rule] The stage that failed is named, or the failure is admitted as unidentified. A generic error is a support ticket with extra steps.
- [canonical rule] A saved credential is never described as a connection.
- [canonical rule] The message states the capabilities that were validated, never the ones that were configured.
- [canonical rule] No fix is suggested that the configurer cannot perform. Where the cause sits with the provider, the message says so.
- [canonical rule] One message per named failure. A fix already given is not repeated on the next attempt.

### Recommended orchestration · notice-then-confirm
1. **active** (service, canonical rule)
   - sent on classification - no wait before it
   - checks: How far did the attempt get?
   - Channel roles: persistent -> in-session
   - Purpose: Confirm the connection is active and name the capabilities that were actually validated rather than the ones that were configured.
2. **fix-auth** (service, canonical rule)
   - sent on classification - no wait before it
   - checks: How far did the attempt get? · Which stage failed?
   - Channel roles: persistent -> in-session
   - Purpose: Say the credential itself was refused and give the one step that re-establishes it.
   - destination: `re-enter-credential` · bound to `connection_attempt_id`
3. **fix-scope** (service, canonical rule)
   - sent on classification - no wait before it
   - checks: How far did the attempt get? · Which stage failed?
   - Channel roles: persistent -> in-session
   - Purpose: Name the specific permission that is missing and where it is granted.
   - destination: `grant-missing-permission` · bound to `connection_attempt_id`
4. **fix-capability** (service, canonical rule)
   - sent on classification - no wait before it
   - checks: How far did the attempt get? · Which stage failed?
   - Channel roles: persistent -> in-session
   - Purpose: Say that access was granted but the minimum operation could not be performed, and name which operation.
   - destination: `capability-check` · bound to `connection_attempt_id` · must not claim: that a saved credential is a connection
5. **generic** (service, canonical rule)
   - sent on classification - no wait before it
   - checks: How far did the attempt get?
   - Channel roles: persistent -> in-session
   - Purpose: Say the attempt failed, that the stage has not been identified, and that nothing further is needed from the configurer while it is looked at.

**Channel roles** (recommended default)
- persistent (email) — the message has to be kept and survive until the person can act on it
- in-session (in-app) — the person is active in the product and the action is taken there
- delivery fallback: same-role-other-channel

### Stops when
- [success] active, with validated capabilities stated (re-entry: a further connection to the same provider is a new instance)
- [failure] still not connected after the named fix (re-entry: a later attempt re-enters at the outcome check; a fix already given is not sent twice)
- [timeout] abandoned before the connection was ever made (re-entry: a new attempt on the same integration starts a fresh instance)
- [handoff] Integration Activation — a failed connection attempt with no stage authoritatively identified

### Configure
- `integration_setup.fix_auth_budget` [config required]: configure integration_setup.fix_auth_budget — This loop runs against a budget fixed when the instance opened; when it is spent the instance takes its timeout path (GLB-24).
- `integration_setup.fix_scope_budget` [config required]: configure integration_setup.fix_scope_budget — This loop runs against a budget fixed when the instance opened; when it is spent the instance takes its timeout path (GLB-24).
- `integration_setup.fix_capability_budget` [config required]: configure integration_setup.fix_capability_budget — This loop runs against a budget fixed when the instance opened; when it is spent the instance takes its timeout path (GLB-24).
- `integration_setup.retry` [config required] (observation-window): configure integration_setup.retry — The period beyond which an unfinished connection is treated as abandoned.
- `integration_setup.touches` [config required]: configure integration_setup.touches — Stage messages are repeated only as retries recur, against a total budget fixed at the first attempt; the budget is the company's, and the plan never repeats a stage message without a new attempt behind it.
- `integration_setup.cooldown` [recommended default]: none — This journey is per the single connection attempt and the integration it configures; a later instance concerns a different the single connection attempt and the integration it configures and no cooldown applies between them.

### Measurement

- guardrails: complaint · message_after_success · unsubscribe

### Reusable rule
A setup failure is only actionable if it names the stage it failed at, and only honest if it admits when it cannot.

### Entity (notes)
- the single connection attempt and the integration it configures
- One instance per connection. A second connection to the same provider has its own credentials, scopes and outcome, and inherits nothing from this one.

### Distinct from
- INT-111 (Integration connection → authenticate → validate → activate) — INT-111 authenticates, checks scope, probes capability and decides whether the connection is active. This journey is what the person configuring it is told about that outcome, and it invents no diagnosis of its own.
- INT-269 (Integration connection broken → reconnect → restored or degraded) — INT-269 addresses an established connection that has broken. Here nothing has ever worked, so there is no prior capability to restore and nothing to describe as degraded.

### Guardrails
1. The stage that failed is named, or the failure is admitted as unidentified. A generic error is a support ticket with extra steps.
2. A saved credential is never described as a connection.
3. The message states the capabilities that were validated, never the ones that were configured.
4. No fix is suggested that the configurer cannot perform. Where the cause sits with the provider, the message says so.
5. One message per named failure. A fix already given is not repeated on the next attempt.

### Technical logic (graph, 14 nodes)
- **t.started** [trigger] (entry, evidence: authoritative)
  - Event id: `integration_connection_attempt_resolved`
  - Integration connection attempt resolved
  - evidence: authoritative
  - requires: a connection attempt recorded against a named integration by a named configurer
  - requires: a recorded outcome from the authentication, scope and capability checks
  - not enough on its own: an integration browsed or selected
  - not enough on its own: a credential entered but never submitted
  - -> c.outcome (node)
- **c.outcome** [condition] (3 branches)
  - How far did the attempt get?
  - -> a.active [Active]: authentication, required scope and the capability probe all passed and the connection is recorded active (node)
  - -> c.stage [Failed at a named stage]: the attempt failed and which stage failed is authoritatively recorded (node)
  - -> a.generic [Failed, stage unidentified]: the attempt failed and no stage is authoritatively identified (node)
- **a.active** [action] (execution: communication)
  - Confirm the connection is active and name the capabilities that were actually validated rather than the ones that were configured. The difference is what stops somebody building on a permission they do not have
  - -> x.active (node)
- **c.stage** [condition] (3 branches)
  - Which stage failed?
  - -> a.fix-auth [Credential]: the provider refused the credential or the authorisation was never completed (node)
  - -> a.fix-scope [Permission]: the credential was accepted but a required permission was not granted (node)
  - -> a.fix-capability [Capability]: credential and permission both passed but the safe probe could not perform the minimum operation (node)
- **a.generic** [action] (execution: communication)
  - Say the attempt failed, that the stage has not been identified, and that nothing further is needed from the configurer while it is looked at. Admitting there is no cause yet beats inventing one - a guessed cause sends somebody to fix what is not broken
  - -> h.diagnose (node)
- **x.active** [exit]
  - active, with validated capabilities stated
  - Detail: a further connection to the same provider is a new instance
- **a.fix-auth** [action] (execution: communication)
  - Say the credential itself was refused and give the one step that re-establishes it. This is the only stage the configurer can usually fix unaided, and it is the one most often buried under a generic error
  - -> w.retry (node)
- **a.fix-scope** [action] (execution: communication)
  - Name the specific permission that is missing and where it is granted. A missing permission reported as a failed setup makes somebody redo an entire connection to change one switch
  - -> w.retry (node)
- **a.fix-capability** [action] (execution: communication)
  - Say that access was granted but the minimum operation could not be performed, and name which operation. This usually sits with a limit on the provider side, so the message points there rather than at the configurer
  - -> w.retry (node)
- **h.diagnose** [handoff]
  - Integration connection → authenticate → validate → activate
  - Detail: a failed connection attempt with no stage authoritatively identified
  - carries: the attempt, its provider and what the configurer has already been told
  - carries: which stages did pass before the failure
  - -> INT-111 (journey)
- **w.retry** [wait]
  - until a further connection attempt is recorded, or the holder removes the connection
  - Detail: timeout after The period beyond which an unfinished connection is treated as abandoned. (configure integration_setup.retry)
  - a half-configured integration nobody returns to is not work in progress and must stop being counted as such
  - engagement does not extend the window
  - -> c.retry [on event] (node)
  - -> x.abandoned [on timeout] (node)
- **c.retry** [condition] (4 branches)
  - What did the next attempt do?
  - -> a.active [Now active]: a later attempt passed every stage and the connection is recorded active (node, back-edge)
  - -> x.unresolved [Failed again]: a later attempt failed at a stage that has already been named to the configurer (node)
  - -> c.stage [Failed at a different stage]: a later attempt cleared the stage that was named and failed at one that has not been named yet (node, back-edge)
  - -> x.abandoned [Removed]: the configuration was removed before any attempt succeeded (node)
- **x.abandoned** [exit]
  - abandoned before the connection was ever made
  - Detail: a new attempt on the same integration starts a fresh instance
- **x.unresolved** [exit]
  - still not connected after the named fix
  - Detail: a later attempt re-enters at the outcome check; a fix already given is not sent twice
