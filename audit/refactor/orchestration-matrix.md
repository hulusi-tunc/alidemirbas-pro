# Channel / orchestration matrix — all 69 public journeys

Phase 1 audit, channel & orchestration slice. Source: `audit/public-journeys-current-state.json`
(canonical + rendered display state), queried per journey. **155 customer-facing communication
stages** across 69 journeys — one row each. RET-24 has none and gets a row saying so.

## The systemic defect, stated precisely

Every communication action in the corpus carries `orchestration.touches[].channelRoles`, an
**unordered set of registers** drawn from four names: `in-session` → in-app, `persistent` → email,
`low-friction` → push, `urgent` → sms/whatsapp. `channelStrategy.roles` expands each role to its
channels. Every one of the 155 stages resolves its channels this way — `node.channel.source` is
`"orchestration.channelRoles x channelStrategy.roles"` on **155 of 155**, with no other tier used.

The renderer then prints **`channelRoles[0]` as "Primary" and every later entry as "Fallback"**.
That is the whole of the Primary/Fallback shape: it is **array order, not behaviour**. **160
display cards** carry it in each locale — 155 customer-facing stages, **plus five internal actions
that are not customer messages at all** (§4.2).

- **144 of 155 stages declare 2–4 channels.** Only 11 declare one.
- **Exactly 2 journeys** (ACQ-287, ACQ-288) contain a node that actually resolves a channel:
  `a.router1` / `a.router2-hv` / `a.router2-std`, which read push-token validity and WhatsApp
  eligibility and write `selected_channel_t1` / `selected_channel_t2`. **Those six stages are the
  only genuine fallbacks the corpus implements** — and all six routers are hidden from the canvas
  (`displayDelta.canonicalNodesNotDrawn`), so the one place the behaviour is real is the one place
  it is not drawn.
- The other **149 stages assert multiple channels with nothing anywhere in the graph that picks
  between them.** Their behaviour is not fallback, not parallel, not routing — it is undefined,
  and the canvas invents fallback to fill the gap.

## Shorthand used in `Current behavior`

| Code | Meaning |
|---|---|
| `UNRESOLVED` | 2+ roles asserted on one action; **no node in the journey reads any signal that picks between them**. "Primary/Fallback" is renderer array order, not behaviour. |
| `ROUTED` | A node in the graph genuinely selects the channel before the send (ACQ-287/288 routers only). |
| `SINGLE` | One channel declared; behaviour is what it appears to be. |
| `NONE` | No customer-facing communication action. |

## Pattern vocabulary

`single` · `sequential` (later touch in a timed series, reached only through a state re-check) ·
`conditional routing` (a real signal read at send time picks exactly one channel; both arms are
legitimate destinations) · `parallel` (two channels at the same moment doing different jobs, sent
once) · `fallback` (the desired channel genuinely cannot be used and another substitutes) ·
`segment arm` noted in Reason where the branch already exists in the graph · `merge` where the
stage should stop being a separate message.

Internal actions (`execution: "human"`, CRM/task/Slack/sales/support/human review) are **not
channels** and never appear in `Final channel(s)`; where a stage raises one it is named in Reason
so the implementer keeps the supporting action.

**On the email share, stated plainly.** 104 of 155 stages land on email alone, and that will look
like standardisation. It is not: it is what this corpus is made of. Read the 69 purposes and the
majority are *statements of record* — order confirmations, refund statements, restriction notices,
renewal terms, remedy decisions, invitations with scope and expiry, loyalty balances with expiry
dates, contractual notices. Those all need the same three properties (room, persistence,
retrievability), so they get the same channel, and the differentiation in this refactor is in the
**pattern and the touch count**, not in channel variety for its own sake. Where the moment is
genuinely different, the channel is: 12 in-app stages where the person is demonstrably in the
product at that second, 7 SMS stages where a short fact has a real and imminent consequence, and
push reduced from 25 journeys to the 3 where a reachability test exists or can be imported.

The two temptations this audit deliberately refused:
- **Adding push to everything with an app.** 29 journeys asserted push; only 2 of them contain a
  node that tests whether a push could actually be delivered. Push survives in 3.
- **Using SMS as escalation.** SMS is the *second* channel on 29 stages today, almost always as the
  "urgent" role on a later touch. It survives only where the message is short, the consequence is
  real and the deadline is enforced by something other than the message: `ACQ-11 a.touch3`,
  `FUL-146 a.delay-update`, `FUL-148 a.correct`, `FUL-265 a.arrived`, `SCH-266 a.remind`,
  `SCH-304 a.checkin`, `SCH-304 a.late-detail`, plus the four parallel last-chance moments.
