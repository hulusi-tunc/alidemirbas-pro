# Marketing Calculator Library — Architecture & Research (Phase 0–12)

Foundation-only pass: candidate universe, taxonomy, formula-family
deduplication, full catalog specs, schema, validator. No new pages were
built in this pass beyond what already ships (`src/lib/calculators.ts`,
15 calculators). See `FINAL REPORT` (chat) for the numbers; this file is
the "why" behind the structural decisions and the open questions.

## 0. What already existed (Phase 0 audit)

- `src/lib/calculators.ts` — 15 shipped calculators (ROAS, CR, CAC, LTV,
  CTR, CPC, CPM, CPL, AOV, A/B significance z-test, Marketing ROI, Profit
  Margin, Retention Rate, Cart Abandonment, Engagement Rate) + 2 text
  tools (UTM Builder, Character Counter). Flat list, no category field,
  one slug per tool, `compute(v) => CalcResult[]`.
- `src/components/CalculatorTool.tsx` / `CalculatorRoutes.tsx` — client
  render + routing, top-level `/calculators` and `/calculators/[slug]`
  (EN + TR), `SiteHeader`/`SiteFooter` chrome — sibling to About/Stack,
  deliberately NOT under `/lab` (see prior session decision).
- No existing calculator taxonomy, formula-family map, or validator —
  this phase's `production/calculators/` folder is new.
- Journey (`/lab/journeys`) and A/B Test (`/lab/ab-testing/library`)
  canonical datasets were read for pattern reference only (schema +
  validator conventions) and were not touched.

## 1–3. Candidate universe, classification, duplicate detection

161 candidates researched across the 10 required disciplines →
`calculator-candidates.json`. Classification counts and the full
formula-family/duplicate map are in `calculator-formula-families.json`,
with a `decision` string per family explaining exactly what folded into
what and why. Two decision patterns recur and are worth stating once
here rather than 18 times there:

- **Same formula, but kept as separate pages anyway**: `cost-per-unit`
  (CPC/CPM/CPA/CPL/CPI/CPV) and the CAC/Logo-Churn/Blended-CAC family.
  The math is identical (`spend / N`), but each is an independently
  named, independently searched, independently benchmarked term —
  advertisers choose "CPC bidding" vs "CPM bidding" as different
  products, not different labels on one number. This matches the
  site's existing convention (CPC and CPM already ship as separate
  pages) rather than inventing a new mode-switcher pattern.
- **Same formula, folded into one tool**: the 16-way `conversion-rate`
  family (Lead CR, Visitor-to-Lead, MQL-to-SQL, Landing Page CR, Install
  CR, Trial-to-Paid CR, …) all fold into the existing generic `cr`
  calculator, which already has industry-neutral input labels
  (conversions/opportunities). This is the brief's own worked example,
  applied literally.

The one **cross-category collision** worth flagging explicitly: Repeat
Purchase Rate (e-commerce) and Repeat Customer Rate (lifecycle-retention)
turned up independently during research as the exact same formula. Only
`repeat-purchase-rate` ships; the other is its `dup` pointer. This is
the kind of duplication the two-pass research process (10 categories
researched somewhat independently) is expected to produce, and the
validator (`validate-calculators.mjs`) would catch it again if it
recurred.

## 4–5. Catalog & mathematical ambiguities

77 calculators recommended (`calculator-catalog.json`, generated by
`_generate-catalog.mjs` from the candidates + families files — never
hand-edit the catalog directly, edit the generator and re-run it, or the
three files will drift). Full Phase-4 field set per entry: formula,
plain-English explanation, typed inputs/outputs, accepted ranges,
validation rules, edge cases, one worked example, related metrics and
calculators, formula family, aliases.

Three calculators intentionally document **multiple legitimate
formulas** rather than picking one silently (Phase 5 requirement):

1. **LTV** — three models exist and are NOT interchangeable:
   - *Simple/historic* (shipped): `AOV × purchase frequency × lifespan`.
     Overstates LTV for low-margin businesses because it ignores cost.
   - *Margin-adjusted/predictive*: `(AOV × frequency × gross margin%) /
     churn rate`. This is the model that should feed LTV:CAC Ratio and
     CAC Payback Period — using the simple model there overstates
     acceptable acquisition spend.
   - *Mobile/ARPDAU-based*: `ARPDAU × average lifetime days`. Same
     underlying question, different input convention because mobile
     apps rarely track AOV/order-frequency in the e-commerce sense.
   - Recommendation: keep one `/calculators/ltv` page, add a model
     selector, and label the output with which model produced it. Do
     not average the three or default silently to one.
2. **A/B test significance** — frequentist (shipped, two-proportion
   z-test) and Bayesian (probability variant beats control) answer
   *different questions* (p-value under a null vs. probability of
   superiority) and are not two ways of computing the same number. Both
   are catalogued as separate tools; neither should be presented as
   making the other obsolete.
3. **CAC variants** (Blended vs. Paid vs. Channel) — same formula body,
   different input population. Only Blended CAC gets its own page (it's
   an independently named, independently searched convention, same as
   the cost-per-unit family); Paid/Channel CAC are just the existing CAC
   calculator used with filtered inputs.

Validation rules worth calling out because they'd be easy to get wrong
silently: **Rule of 40** adds two percentages as percentage points, not
compounding them; **CAC Payback Period** requires the gross-margin
adjustment (omitting it is the most common real-world error in this
calculation); **GRR vs NRR** share one input set but GRR is capped at
100% (excludes expansion) while NRR is not.

## 7. Information architecture

```
/calculators                      hub — category filter, search
/calculators/[slug]                detail page (existing pattern, reused)
```

**Category URLs (`/calculators/advertising` etc.) — recommend NOT
building them in this phase.** With 77 calculators across 10
categories (avg. ~8 per category), a dedicated category route adds a
navigation layer without enough inventory per category to justify a
whole page; the hub's category filter already does this job in one
click. Revisit only if the catalog roughly doubles.

Detail page keeps the shipped `/calculators/[slug]` pattern (top-level,
`SiteHeader`/`SiteFooter`, NOT nested under `/lab` — this was an
explicit prior-session correction and nothing in this research changes
it). Breadcrumb: Calculators → [Category] → [Calculator name].

## 8. Relationship graph (data model, not yet wired into the site)

```
Calculator ↔ Calculator      relatedCalculators[]   (same formula family, e.g. CAC ↔ LTV:CAC Ratio)
Calculator ↔ Metric/Concept  relatedMetrics[]        (named business concept, may or may not have its own page)
Calculator ↔ Journey         NOT YET MODELED — needs a real content review, not guessed links
Calculator ↔ A/B Test        NOT YET MODELED — same
```

`relatedCalculators` in the shipped catalog is derived two ways: formula
family co-membership (e.g. NRR ↔ GRR, both live in one tool) and a
name-match against each entry's own `relatedMetrics` text (e.g. CAC's
`relatedMetrics: ["LTV:CAC Ratio", "CAC Payback Period"]` resolves to
real slugs automatically). Nothing here was invented purely to create
internal links — a calculator with zero natural relations stays
unlinked and the validator surfaces that as a warning, not an error, so
it stays visible rather than silently papered over.

Journey/A/B-test cross-links are deliberately **not** modeled yet. The
brief's own examples (Cart Abandonment → Cart Recovery Journey →
Checkout A/B Tests) are plausible but would require actually reading
which of the 255 journeys and 211 A/B tests are topically real matches —
guessing at scale here would produce exactly the "hundreds of weak
relationships" the brief says not to invent. Open question, not a gap
to silently fill.

## 9. Canonical calculator template (information architecture only)

Required for every calculator:
```
Header (name, one-line description)
Inputs
Result
Formula (formulaPlainEnglish)
```

Optional, calculator-specific:
```
Interpretation / benchmark note   — only where a number needs context to read (e.g. LTV:CAC "3x+ is healthy")
Model/mode selector                — LTV, Break-Even, N-Day Retention, Abandonment stage
Example                            — worked example from exampleInput/exampleOutput
Related metrics / calculators
FAQ
```

A CTR calculator needs Header + Inputs + Result + Formula and nothing
else. Sample Size Calculator, Bayesian Probability, and SRM Check need
the Interpretation module (statistical results are actively misleading
without it) — this is exactly the `classification: calculator-educational`
flag already in the catalog; content-length should follow that flag,
not be uniform across all 77 pages.

## 10–11. Explicitly out of scope this phase

No SEO copy, no FAQ answers, no title/meta polishing, no visual design.
Content slots are named (`definition`, `formulaExplanation`, `example`,
`interpretation`, `benchmarks`, `faq`) in the template above; none are
filled in.

## 12. Validation

`validate-calculators.mjs` (no external deps) checks: unique
candidate/catalog ids and slugs, valid categories/subcategories against
the taxonomy, classification/priority enums, every `duplicate-variant`
has a valid `dup` target and every family's `foldedVariants` entry is
actually classified as `duplicate-variant` (catches exactly the
kind of drift found and fixed during this pass — see below), every
`calculator`/`calculator-educational` candidate is claimed by exactly
one family, no self-referencing `relatedCalculators`, every
`formulaFamily` resolves to a real family id, slug hygiene (no
leading/trailing/double hyphen).

Warnings (kept as warnings, not resolved by editing data): near-identical
names, identical formula strings across unrelated families, calculators
with 5+ inputs, calculators with zero related calculators, alias
collisions across different calculators, and a standing tripwire on the
LTV entry's plain-English description losing its "multiple models"
language.

**Current status: 0 errors, 1 warning** (`bayesian-probability-to-beat`
has 6 inputs — genuinely true, a 2x2 test config plus a prior; left as
a warning rather than artificially trimmed). During generation the
validator caught two real inconsistencies before this report was
written: `logo-churn`'s subcategory belonged to a different top-level
category than the one it was filed under, and `break-even-roas` was
classified `calculator` in the research file while the formula-family
file said it folds into `break-even-point` — both are exactly the
class of drift a re-runnable validator exists to catch, and both are
fixed in the committed files, not hidden.

### Source of truth

`production/calculators/calculator-catalog.json` (generated by
`_generate-catalog.mjs`) is the only place calculator metadata is
authored. `src/lib/calculators.ts` (the pre-Phase-1 hand-written array)
was deleted - there is exactly one calculator dataset now, not two.
`src/lib/text-tools.ts` keeps the 2 non-formula tools (UTM Builder,
Character Counter) separate, since they have no formula/catalog entry
by design.

### Architecture

```
calculator-catalog.json  (Phase 1 source of truth, server-only)
        ↓  calc-catalog.ts (loader + slim RuntimeCalcSpec projection)
        ↓  [crosses server→client boundary as plain serialized data]
CalculatorTool.tsx (client): renders inputs from RuntimeCalcSpec
        ↓  calc-validate.ts: raw strings → validated {values} or {errors}
        ↓  calc-registry.ts: getCompute(slug)(values) → raw outputs
        ↓  calc-format.ts: formatByUnit(value, unit) → display string
```

- **`calc-catalog.ts`** (server-only-safe, never imported by a "use
  client" file): typed loader over the JSON, `LIVE_CALCULATOR_SLUGS`
  (the 34-item allowlist), `getCalcSpec`/`getAllLiveSpecs`, and
  `toRuntimeSpec` - the slim projection that drops
  `validationRules`/`edgeCases`/`acceptedRanges`/`aliases` before a
  spec reaches the client, since none of that prose is needed to render
  or run a calculator (see Bundle impact below).
- **`calc-registry.ts`** (client-safe, zero imports, zero deps): one
  pure `(inputs) => outputs` function per live slug. No React, no JSON
  import - independently testable, which is exactly what
  `test-calculators.mjs` does.
- **`calc-validate.ts`**: parses/validates raw form strings against a
  spec's `inputs` (required/invalid/negative/enum-membership), separate
  from computation.
- **`calc-format.ts`**: the one place `%` vs `percentage points` vs
  `x (multiplier)` vs `currency` get formatted, so that distinction is
  correct once rather than reimplemented per calculator.
- **`CalculatorTool.tsx`**: generic renderer driven entirely by the
  spec. Two specialized branches exist because the interaction is
  genuinely different, not because of formula complexity: a mode
  selector (LTV only) and a stage-list editor (the multi-step funnel
  tool's array input) - everything else (33 of 34 calculators, all
  inputs) goes through the same scalar/enum field renderer.

the catalog and outside the chosen batch, but were migrated anyway -
leaving them on the old `src/lib/calculators.ts` engine while everything

**34 live calculators**, not 32.

|---|---|---|

| `cart-abandonment` → catalog id `cart-abandonment-rate`, **URL kept as `/calculators/cart-abandonment`** | unchanged | Additive: a `stage` selector (cart/checkout) was added, defaulting behavior identical to the old cart-only calculation when "cart" is chosen. No output removed. |

Two catalog research-ids (`ab-test-significance`, `cart-abandonment-rate`)
collided with the shorter URLs already public from before Phase 1
existed. Per "preserve existing public URLs whenever possible": a
`SLUG_OVERRIDES` map in `_generate-catalog.mjs` makes the catalog's
`slug` field (and every `relatedCalculators` reference to it) emit the
original short URL, while the research `id` internally stays the
descriptive Phase 1 name for family/candidate cross-references. **No
redirect is required** - both URLs were never live as two different
paths; only one was ever public, and it still resolves.

### Multi-mode: LTV

Phase 1's catalog only captured the simple model's inputs, even though
the architecture doc's own Phase 5 section documented three legitimate
LTV models. That gap was fixed at the source (not patched in the
component): `_generate-catalog.mjs` now carries an explicit `modes`
array on the `ltv` catalog entry (`simple`, `margin-adjusted`,
`mobile-arpdau`), each with its own formula/inputs/outputs, validated
by an extension to `calculator-schema.json`. `CalculatorTool.tsx`
renders a mode selector when `spec.modes` is present; switching modes
swaps the entire input set and formula display, and the result label
always names which model produced it, per the brief's explicit
requirement not to imply one model is universally correct.

### Data bugs found and fixed during implementation

Per Phase 2 §0 ("fix genuine errors at the source, document the
change"), five real Phase 1 data defects surfaced while building against
the catalog, not while re-reviewing it:

1. **`sample-size-calculator`'s own `validationRules` flagged an
   unresolved ambiguity** (relative vs. absolute MDE) and the
   documentation example (30,405) didn't reproduce from its own
   `exampleInput` under either reading. Resolved explicitly: `mde` is a
   **relative** lift (e.g. `10` = "detect a 10% relative improvement"),
   converted to an absolute effect internally as `baselineRate × mde`.
   `exampleInput`/`exampleOutput` corrected to `29,827` (verified by
   `test-calculators.mjs`, not hand-computed).
2. **Inconsistent `%`-field example convention**: some `exampleInput`
   percentage values were written as decimals (`0.75`) and others as
   whole numbers (`30`), with no rule distinguishing them. Standardized
   on "whole number as a human types it" (matches the real UI: `%`
   fields are divided by 100 during parsing) and fixed `cac-payback-period`
   and `sample-size-calculator` to match.
3. **`test-duration-estimator`'s example was internally inconsistent**
   ("31 days (5 weeks)" - 31 is not a multiple of 7). Corrected to
   "35 days (5 weeks)", matching both the round-up-to-week rule and the
   corrected sample-size number it derives from.
4. **`funnel-analysis-multistep` and (P2, not in this batch)
   `multi-variant-test-significance`/`srm-check` had `exampleInput`/
   `exampleOutput` values authored as stringified arrays** (e.g.
   `"[{label:'Visit',count:10000},...]"` as a JSON string) instead of
   real arrays - unusable as actual compute input. Fixed to real
   array/object values for all three.
5. **Two candidate names already ended in "Calculator"**
   (`sample-size-calculator`, `confidence-interval-calculator`), so the
   generator's `name + " Calculator"` suffix produced a doubled name on
   the live related-calculators links. Fixed the generator to detect
   and skip the redundant suffix; added a validator check
   (`validate-calculators.mjs`) so a future doubled name fails the
   build instead of shipping.

All five were caught by either `test-calculators.mjs` (bugs 1-3) or
direct browser review of the shipped page (bugs 4-5), not by inspection
of the JSON alone - the validator's structural checks (Phase 1) cannot
catch an arithmetic error or a wrong string, only a malformed shape.
